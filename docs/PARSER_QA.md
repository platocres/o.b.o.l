# Parser QA

Obol parsers are hand-written, rule-based evidence extractors. They live in
`obol/parsers.py` and run through one entrypoint:

```text
tool stdout/stderr
-> parse_action_output(...)
-> narrow Fact(kind, scope, value, state, source)
-> planner, findings, report, and web surface
```

They are not generated by an LLM at runtime. A parser should recognize stable tool
signals and map them to the narrowest fact the output actually proves.

## Parser Contract

Every parser must follow these rules:

- Parse tool-output shape, not walkthrough-specific names, passwords, hosts, or
  lab shortcuts.
- Prefer structured output when the tool reliably provides it. Text parsing is
  acceptable for common human-readable output, but it needs fixture coverage.
- Preserve source lineage. Every fact should keep the command or run source that
  produced it.
- Record metadata as metadata. Banners, HTTP headers, titles, redirects, SNMP
  system info, and host keys are context, not access.
- Do not turn authentication into a shell. A successful SSH or FTP login proves
  service authentication, not a foothold. SSH only proves a Linux shell when output
  such as `uid=` / `id` proves command execution.
- Do not turn service discovery into vulnerability claims. Open ports and service
  versions unlock next moves; they do not prove exploitation.
- Add negative fixtures for failure, timeout, and misleading-output cases.

## Fixture Corpus

The fixture corpus lives under:

```text
tests/fixtures/parser/
```

The manifest is:

```text
tests/fixtures/parser/manifest.json
```

Each case declares:

- `id`: stable fixture name.
- `action_id`: the action identity passed into `parse_action_output`.
- `command`: the command used as both parser input and fact source lineage.
- `stdout` / `stderr`: fixture transcript paths.
- `expected_supported_kinds`: fact kinds that must be supported.
- `expected_refuted_kinds`: fact kinds that must be refuted.
- `expected_facts`: optional scoped/payload assertions.
- `forbidden_supported_kinds`: fact kinds that must not be supported.
- `allow_default_forbidden_supported_kinds`: explicit exceptions for fixtures that
  are supposed to prove access, such as SSH `id` output.

The harness is:

```text
tests/test_parser_fixtures.py
```

Run it directly:

```bash
python3 -m pytest tests/test_parser_fixtures.py -q
```

## Current Coverage Matrix

| Fixture | Tool Shape | Positive Claims | Forbidden Claims |
|---|---|---|---|
| `nmap_service_script_metadata` | nmap service/script output | host up, ports, SSH/FTP/DNS/SNMP/HTTP/RDP reachability, SSH host keys, FTP anonymous login, SNMP info, HTTP redirect, web tech | credentials, footholds, admin, loot, vulnerabilities |
| `http_curl_whatweb_metadata` | curl headers plus whatweb plugins | HTTP response, redirect, server header, title, tech fingerprints | credentials, web auth, upload/LFI proof |
| `nxc_ssh_ftp_auth_context_only` | NetExec SSH/FTP success lines | service authentication and usable credential | shells, footholds, admin |
| `nxc_failed_login_refutes_validation` | NetExec failed SMB login | SMB reachability and refuted credential validation | usable credential or SMB authentication |
| `ssh_banner_no_shell` | raw SSH banner | SSH reachability and banner | shell, foothold, admin |
| `ssh_id_proves_linux_shell` | SSH command execution showing `uid=` | shell and Linux foothold | admin unless uid is root |
| `snmp_timeout_no_facts` | SNMP timeout | no facts | all claims |
| `ftp_named_login_not_anonymous` | FTP successful named login transcript | FTP reachability and banner | anonymous FTP or credential availability |

## What This Proves

The corpus proves the parser behavior for the checked-in output shapes. It also
proves that those shapes do not overclaim the forbidden higher-value facts.

It does not prove that every version of every tool is covered. Parser confidence
should rise as more anonymized real outputs are added from labs, CTF boxes, and
operator runs.

## Adding a Parser

Use this workflow:

```text
1. Add or update the narrow parser in obol/parsers.py.
2. Add at least one positive fixture transcript.
3. Add at least one negative or anti-overclaim fixture when the parser could be
   confused by similar text.
4. Assert exact payload details for the important facts, not just fact kinds.
5. Run tests/test_parser_fixtures.py and the full suite.
```

Fixtures may be based on real tools, but must be anonymized and generalized.
Do not encode lab names, box-specific solution paths, magic passwords, or
hardcoded route logic. Golden fixtures are regression locks, not recipes.
